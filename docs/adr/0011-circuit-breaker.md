# ADR-0011：渠道熔断与恢复

- 状态：已接受并实施
- 日期：2026-10-18
- 决策人：用户、架构

## 背景

线上 8 天的错误日志里，`502 all channels for this model are temporarily unavailable (circuit open)` 有 1453 条，
是数量最多的错误，比所有真实的上游错误加起来还多；七成以上来自 gpt-6.1-sol。每次熔断持续 1–7 分钟，期间 30–130 个请求直接失败。
排查后的原因：

1. **单渠道模型**：GPT 系列只有一个渠道（自有号池）。熔断后没有别的渠道可换，所有请求立刻 502。
   「跳过坏渠道、换下一个」的前提在这里不成立。
2. **触发源大多是上游的短暂故障**：`Bad Gateway`、`servers are currently overloaded`、`no available server`
   （号池网关重启或过载），以及 60 秒内没有返回响应头的 504。并发高时，同一秒内一批请求一起失败，瞬间凑够「5 次且 ≥50%」。
3. **429 也会熔断**：`usage limit has been reached` 只说明上游账号的额度用完了，渠道本身是好的，却让整个渠道下线。
4. **熔断粒度是整个渠道**：gpt-6-luna 额度用完，同一渠道上的 gpt-6.1-sol 也跟着下线。
5. **恢复慢**：冷却固定 30 秒，主动探测每 15 秒一次；半开状态只放行 **1 个**真实请求，而且这个请求要等**整个流式响应结束**才算成功——
   一个 2 分钟的流就让其他请求多等 2 分钟。

## 决策

### 1. 按类型处理失败（`channel.FailKind`）

| 失败 | 处理 |
|---|---|
| 连接失败、5xx、响应格式错误 | `transient`：计入**渠道**，权重 1；先在请求内短重试（见 3） |
| 响应头超时 | `timeout`：计入渠道，权重 0.5 |
| 401 | `auth`：计入渠道，打开后冷却从 60 秒起（最长 10 分钟） |
| 403 | `model`：只计入该**渠道 × 模型** |
| 429、上游返回「quota / usage limit / exhausted / rate limit」 | `rate_limit`：**不熔断**，只暂停该渠道 × 模型，时长取 `Retry-After`（默认 10 秒，最长 5 分钟） |
| 其他 4xx、上下文超长、客户端断开 | 不计入健康状态（不变） |

### 2. 两级熔断：渠道级 + 渠道 × 模型级

请求同时受渠道和模型两级状态约束：渠道级故障影响该渠道的所有模型；模型级问题（403、限流暂停、模型专属失败）只影响该模型，
渠道上的其他模型照常服务。

### 3. 打开条件：按秒合并突发

在 60 秒窗口内，按 1 秒分桶统计：每个有失败的桶最多计 1（超时 0.5），**加权失败秒数 ≥ 3**，且失败请求 **≥ 50%** 才打开。
一次上游重启让同一秒内几十个并发请求一起失败，只算 1 秒。

### 4. 请求内同渠道短重试

尚未向客户端输出任何内容、失败属于 `network` / `server_error`、并且**没有其他候选渠道和回退模型**时，
在同一渠道上退避重试：0.5 秒 → 1.5 秒 → 3 秒（±20% 抖动，总等待不超过 6 秒；上游给了 `Retry-After` 则按它，超出预算就放弃）。
重试与其他尝试一样计入该档位的 `maxAttempts`（默认 3，即最多再试 2 次；可在系统设置中调大到 5）。
同一请求的多次重试只在最终失败时向熔断器记 1 次失败，成功则不记。

### 5. 最后手段：不因为熔断直接拒绝

某个模型的所有候选都处于熔断或暂停时，不立即报错，而是按「最快恢复」的顺序再尝试这些渠道（`Breaker.ForceAllow`），
每个熔断状态同时最多 3 个这样的请求。上游其实已经恢复时，用户无感；仍然失败时按普通失败返回。
冷却期内这类请求失败不会延长冷却。

### 6. 恢复

- **自适应冷却**：首次打开冷却 5 秒，每次半开探测失败翻倍，最长 60 秒；真实请求成功后归零。主动探测器的成功只关闭熔断、不清零退避级别
  （模型列表能访问不代表请求能成功）。
- **半开并发探测**：冷却结束后同时放行最多 3 个请求，任何一个成功就关闭。
- **流式请求在收到上游 200 响应头时就记为成功**，不再等流结束；之后流中断照常记一次失败。
- **主动探测**每 3 秒检查一次冷却结束的渠道（模型列表 / 插件 `health.check`），上游恢复后几秒内回到轮换。

### 7. 真的不可用时：503 + Retry-After

连最后手段都无法尝试（各熔断的探测名额已满）时，返回 **`503 upstream_unavailable`** 和 `Retry-After`（最早恢复的熔断剩余秒数，至少 1 秒），
OpenAI / Anthropic SDK、Codex、Claude Code 会据此自动退避重试。

### 8. 可观测性

渠道的 `health` 增加 `reason`（`failures` / `auth`）、`retryAt`、`rejectedRequests` 与 `models`（每个模型的 `open` / `paused` / `degraded`、恢复时间、最近错误）。
管理后台的渠道列表与详情页显示这些信息。渠道级打开 / 恢复照常发送 `channel.unhealthy` / `channel.recovered` 通知；模型级状态不发通知。

## 后果

- 上游短暂重启：请求延迟几秒，而不是 1–7 分钟的连续 502。
- 上游真正长时间故障：熔断照常打开；每个熔断最多 3 个并发请求去试探，其余请求立刻拿到 503 + Retry-After。
- 熔断状态仍在进程内维护，重启后归零；多实例部署时各实例独立（与 ADR-0010 一样按单实例运维）。
- 测试可以通过 `app.Options.Breaker` / `channel.RegistryOptions.Breaker` 调整分桶与阈值（集成测试用 `NoMerge`，每次失败单独计数）。
