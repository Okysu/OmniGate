# ADR-0006：计费、周期配额、兑换码与结算币种

- 状态：**已接受**（2026-10-08 用户确认全部 5 项细节，均按建议执行）
- 日期：2026-10-08
- 详细契约：[contracts/billing-and-quota.md](../contracts/billing-and-quota.md)

## 背景

原需求的待确认项 4：“只统计上游成本，还是同时对下游计价、扣减余额、充值”。用户补充：

- 需要对下游计费，支持**按次**、**按额度**、**周期内限额**（例如云厂商的“每 5 小时”“每周”限额），并且计费方式可以由插件扩展；
- 支持用**兑换码**购买订阅或充值 API 积分；
- 可以设置货币单位（如美元）。

## 决策

### 1. 两本账分开

- **成本账**（cost）：上游实际花了多少，按渠道/模型的成本价版本计算，每次上游尝试都记录（含重试、回退）。
- **收入账**（charge）：向下游用户收多少，按售价版本、用户组倍率或订阅配额计算，**每个网关请求最多收一次**。

### 2. 结算币种

- 每个部署只有一个**结算币种**（ISO 4217，`OMNIGATE_CURRENCY`，默认 USD）。首次启动写入 `system_settings`
  并锁定；以后修改环境变量不会生效（会告警），需要显式迁移。
- 上游价格可以用其他币种标价（例如 DeepSeek 用 CNY），通过**手动维护、带版本的汇率表**换算；
  成本事实同时记录原币金额、换算金额和汇率版本。⚠️ 汇率是否手动维护（默认是）。
- 钱包余额直接以结算币种计（“API 积分” = 结算币种金额）。是否需要“1 美元 = N 积分”这样的展示别名，留作展示层配置。

### 3. 统一的配额原语：计量 × 窗口 × 上限

“按次、按额度、5 小时、每周”都表达为**配额规则** `QuotaRule = (meter, window, limit, scope, filter, onExceed)`：

- **计量 meter**：`requests`、`tokens.input|output|cache_read|cache_write|reasoning|total`、`charge`（按售价折算的金额）、
  `custom:<name>`（由计费插件计算，例如“Opus 按 5 倍计”的加权点数）。
- **窗口 window**：
  - `calendar`：按日/周/月对齐到指定时区（例如每周一 00:00 Asia/Shanghai 重置）；
  - `rolling`：滑动窗口（最近 D 时长的累计，按 1–5 分钟分桶近似）；
  - `session`：首次使用时开始、持续 D 时长的锚定窗口（类似 Claude 的“5 小时会话窗口”）；
  - `period`：与订阅周期对齐（从购买日起每月）；
  - `lifetime`：整个订阅期内的总量（如试用 100 次）。
- **范围 scope**：订阅、用户、Gateway Key、模型组。
- **超额行为 onExceed**：`block`（返回协议格式的 429 和 `retry-after`）、`overflow_to_wallet`（超出部分改从钱包按量扣费）。
  ⚠️ 默认值待确认（建议：套餐上可配置，默认 `block`）。

套餐（Plan）就是一组配额规则 + 覆盖的模型范围 + 有效期，例如：

| 套餐 | 规则 |
| --- | --- |
| 按次包 | `requests` / `lifetime` / 1000 |
| 月度额度 | `charge` / `period(1 个月)` / 20 USD |
| 类 Claude Pro | `custom:weighted` / `session(5h)` / 45；`custom:weighted` / `calendar(week)` / 500 |

订阅在创建时**快照**套餐规则，管理员之后修改套餐不会追溯影响已有订阅。

### 4. 钱包（按量付费）

- 每个用户一个钱包，余额 + 预留金额；所有变动写入**只追加的账本** `ledger_entries`（记录变动后余额），钱包表只是缓存。
- 请求前按估算最大成本**预留**（max_tokens × 售价），请求结束后按实际金额结算并释放预留；默认不允许透支。

### 5. 兑换码

- 类型：`wallet_credit`（充值金额）、`plan`（开通或续期某套餐 N 个周期）；预留 `invite`（注册邀请）。
- 管理员按批次生成，明文**只在生成时展示一次**（支持 CSV 导出）；数据库只保存 SHA-256 摘要与前缀（ADR-0008）。
- 约束：总次数、每用户次数、生效/过期时间、批次备注；兑换在事务内原子完成并写审计；兑换接口按用户与 IP 限流，
  码长 ≥ 100 bit 熵，防止暴力枚举。
- ⚠️ 首期**只做兑换码，不接在线支付**；预留 `payment_provider` 接口，支付成功后走与兑换相同的“发放（grant）”路径。

### 6. 计费插件的边界

插件**只负责“算多少”**，宿主负责“够不够、扣多少、记哪本账”：

- 插件可以声明自定义计量（`meters`）及其纯函数 Hook `computeUnits(usage, ctx)`，也可以提供套餐模板（`planTemplates`）；
- 可选 `estimate(request)` Hook 用于请求前估算（严格 5ms 超时，超时则回退到宿主估算）；
- 窗口判断、计数器原子递增、账本写入、预留与释放**全部在宿主 Go 代码中**完成，不进入 JS 沙盒。

原因：金额正确性与并发原子性不能依赖沙盒内代码；同时插件版本会记录在每条用量事实上，便于追溯。

此外区分**上游账号限额**：渠道插件可以通过 `quota.get` 能力上报上游账号自身的 5 小时/每周限额状态，
路由据此避开已耗尽的渠道。这和对下游出售的套餐限额是两套独立机制。

### 7. 结算一致性

- 每个请求以 `request_id` 为幂等键；收入事实对 `request_id` 唯一，重试和回退不会重复扣费；成本事实按尝试逐条记录。
  ⚠️ 默认只向下游收取成功那一次（失败尝试的上游成本由平台承担），待确认。
- 流式请求中途断开：上游已经产生的用量照常计费；上游没有返回 usage 时用分词器估算，并标记 `estimated=true`。
- 配额是**软上限**：请求前检查，请求后入账。并发请求可能使计数略超上限（上界 ≈ 并发数 × 单请求用量）；
  超过之后新请求会被阻断。钱包通过预留机制保证不透支。
- 历史账单固定引用当时的价格版本、汇率版本和套餐快照，不随新价格变化。

## 已确认（2026-10-08）

1. 首期只做兑换码，不接在线支付（预留 `payment_provider` 接口）。
2. 订阅配额超额行为在套餐上可配置，默认 `block`。
3. 重试/回退产生的失败上游成本**不向下游收取**，只计入成本账。
4. 非结算币种的上游价格使用管理员手动维护、带版本与生效时间的汇率换算。
5. 结算币种首次启动后锁定（已实现）。

文中带 ⚠️ 的位置均以上述结论为准。
