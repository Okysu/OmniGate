# ADR-0002：插件执行引擎——Goja 嵌入式运行时

- 状态：已接受（2026-10-08 用户确认选择 Goja）
- 日期：2026-10-08

## 背景

渠道插件用 JavaScript/TypeScript 编写，需要在请求热路径（请求转换、流式解析）与后台任务
（余额查询、模型发现）中执行。需求要求：超时、CPU/内存限制、可取消、稳定的错误边界，
且插件不得访问宿主文件系统、进程、数据库或任意网络。

## 可选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **Goja**（纯 Go ES 引擎） | 纯 Go、单二进制；与 Go 互调成本低、性能好；`Interrupt` 可中断死循环 | **无每实例内存上限**；非 goroutine 安全，需要运行时池 |
| QuickJS（转译/WASM） | 可硬性限制内存 | 慢于 Goja；Go 互调更繁琐 |
| 独立进程 Worker（Deno/Node） | 隔离最强 | 多一个部署组件；每次 Hook 跨进程，流式延迟高 |

## 决策

采用 **Goja**，并通过下列设计弥补其限制。引擎隐藏在 `PluginRuntime` 接口之后，
未来可为“不受信任插件”增加 QuickJS-WASM 或独立进程后端而不改插件 API。

### 1. 编译与加载

- 插件源码（多文件 TS/JS）在**发布草稿时**由服务端 esbuild（Go API，纯 Go）打包为单文件，
  目标 ES2017；禁止 `import` 宿主未声明的模块，SDK 通过全局 `og` 注入。
- 每个插件版本编译一次为 `*goja.Program` 并缓存（按内容哈希）。

### 2. 运行时池与状态

- 每个插件版本维护一个运行时池；每次 Hook 调用从池中借出一个运行时，归还前清理调用上下文。
- 插件模块作用域在运行时之间**不共享**，插件必须按无状态编写；宿主在调用 N 次或空闲 T 时间后回收运行时，
  防止模块级缓存无限增长。
- 流式解析：一个流式请求在整个生命周期内持有同一运行时，`parseStream(chunk, state)` 的 `state` 由宿主保存。

### 3. 热路径最小化

- 内置协议（OpenAI Chat/Responses、Anthropic Messages）的请求构造与 SSE 解析由**原生 Go** 实现。
- 插件只覆盖声明过的 Hook；未覆盖的 Hook 不进入 JS。“继承 OpenAI 兼容协议 + 余额卡片”这类插件
  在请求热路径上**零 JS 调用**。

### 4. 资源限制

| 资源 | 机制 |
| --- | --- |
| 时间/CPU | 每次 Hook 设置墙钟超时（默认：请求 Hook 50ms，单个流式分片 20ms，能力 Hook 10s），超时与 `context` 取消都会调用 `vm.Interrupt`；每个插件版本有并发执行上限（信号量），限制 CPU 占用份额 |
| 内存 | **无硬上限（Goja 限制）**。缓解措施：① 输入上限（请求体、分片、宿主 API 返回值都有字节上限）；② 输出上限（Hook 返回值在序列化时限长）；③ 看门狗：有插件执行时每 10ms 采样 `runtime/metrics` 堆大小，超过软上限就中断运行最久的插件执行，并记录违规；④ 建议运维通过环境变量设置 `GOMEMLIMIT`（OmniGate 不自动设置）；⑤ 同一插件版本连续违规会被熔断（自动停用并告警） |
| 网络 | 只能用 `og.fetch`：域名白名单来自 manifest 权限；自定义 Dialer 在**解析后**校验 IP，拒绝环回、链路本地、私网、云元数据地址，并禁止重定向到白名单外 |
| 密钥 | 插件拿到的只是句柄。`signRequest` 通过占位符（如 `og.secret("apiKey")`）声明头部值，宿主在发送时替换；HMAC 等签名由宿主函数 `og.crypto.hmac(handle, data)` 在 Go 侧完成。读取明文需要单独的高风险权限 `secrets:plaintext` |
| 存储 | `og.storage` 按（插件，渠道）隔离，有键数与字节配额 |
| 宿主访问 | 不注入 `require`、`process`、文件系统、定时器以外的任何全局；`eval`/`Function` 构造器在加载时冻结或禁用 |

### 5. 谁可以运行代码

- 插件安装/发布需要 `plugins.manage` 权限（系统管理员、渠道管理员）。普通用户只能**选择**已安装插件来创建私有渠道，
  不能上传代码。这样把“恶意代码”的来源限制在受信任的管理员范围内，降低内存无硬上限带来的风险。

## 影响与代价

- 验收标准中“过量内存被阻断”调整为：**看门狗中断该插件执行、网关进程保持可用、违规被记录并可触发熔断**；
  不承诺单个插件的精确内存硬上限。选项说明中已写明 Goja 无法限制内存，用户在知晓这一点后选择了 Goja；该调整需在本轮总结中再次确认。
- 若未来开放“普通用户上传插件”或插件市场引入不受信任代码，需要重新评估并引入硬隔离后端（新 ADR）。

## 技术验证结果（2026-10-08，Round 3 开始前）

测试代码见 `server/internal/plugin/engine` 的测试与基准（最初的验证脚本已并入）。

| 验证项 | 结果 |
| --- | --- |
| esbuild（Go API）打包多文件 TS，虚拟文件系统，只允许 SDK 与相对导入 | 3ms，产物 3.5KB；导入未知模块在编译期报错 |
| ES2017 目标下的 `async/await`、私有字段、可选链、展开 | Goja 运行正常；宿主函数同步执行并返回已决议的 Promise，调用结束时 Promise 已完成 |
| 死循环 | 50ms 超时准时中断；中断后运行时可继续复用 |
| 内存看门狗（`runtime/metrics` 每 5ms 采样） | 堆增长超过 64MiB 时触发，131ms 内中断内存炸弹，进程正常 |
| 运行时池 | 每个运行时约 47KiB，创建 + 加载插件 37µs；1000 个并发流约 47MB |
| 单次能力调用开销 | 约 13µs |

结论：方案可行，按本 ADR 实施。看门狗以“进程堆增长量”为信号，多个插件同时运行时会中断运行时间最长的那一个，存在误伤正常插件的可能（已记录违规并可熔断，阈值可配置）。
